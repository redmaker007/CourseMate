# 课程成员关系状态与私聊失败展示规范

状态：已确认
日期：2026-09-19

## 背景

课程群成员列表目前只读取成员 ID、显示名称和头像。除当前成员本人外，页面统一显示“添加好友”，因此已建立好友关系的成员仍会看到错误入口。提交申请后，数据库会正确返回 `already_friends`，不会创建重复申请；问题位于读取模型和页面展示，而不是好友申请写入边界。

邮箱搜索与课程成员列表必须遵守同一条业务规则：只要好友关系仍为 active，隐藏、单向拉黑、被对方拉黑或双向拉黑都不能把双方显示成可再次添加的非好友。

## 目标

- 课程成员列表准确展示当前成员与其他课程成员的好友关系。
- 已是好友时显示“已是好友”和“发消息”，直接进入已有私聊。
- 待处理申请或联系限制存在时，不显示重复的“添加好友”。
- 邮箱搜索不得把 active 好友显示成可再次申请。
- 好友关系、联系限制和消息发送能力分别建模，避免互相覆盖。
- 数据库继续作为好友申请和消息发送的最终权限边界。
- 真正发送失败的本地消息显示可访问的红色失败标记，并按失败类型决定是否允许重试。

## 非目标

- 不改变好友申请的有效期、限流或接受流程。
- 不改变删除好友、隐藏好友或拉黑的业务含义。
- 不允许课程成员列表直接接受或拒绝好友申请；收到申请时引导到好友页面处理。
- 不为已知不可发送的会话开放输入框，再制造一条必然失败的消息。
- 不修改已经应用的历史 migration。
- 不在本次工作中新增 ADR；本规范描述的是可逆的读取模型和界面行为。

## 术语与不变量

### Active 好友

`friendships.active = true` 表示双方仍是好友。以下状态不得改变这个判断：

- 当前成员隐藏该好友；
- 当前成员拉黑对方；
- 对方拉黑当前成员；
- 双方互相拉黑；
- 当前学校上下文暂时使私聊只读。

### 隐藏

隐藏是当前成员自己的好友列表展示偏好，只影响好友出现在哪个列表，不改变好友关系，也不改变另一方的数据。

### 联系限制

联系限制表示任一方向存在拉黑。它可以与 active 好友关系同时存在。联系限制阻止新的好友申请或消息发送，但不删除好友关系和已有私聊历史。

### 发送能力

发送能力独立于好友关系：

- `allowed`：当前允许发送新消息；
- `blocked`：存在拉黑限制，历史可读但不能发送；
- `readonly`：好友关系、成员删除或当前学校权限不允许发送，历史仍可读。

## 状态优先级与页面行为

好友关系、联系限制和发送能力必须分别计算。页面按以下规则展示：

| 好友关系 | 待处理申请 | 联系限制 | 课程成员列表 | 私聊行为 |
|---|---|---|---|---|
| active | 任意 | 任意 | “已是好友” + “发消息” | 允许进入历史；是否可输入由发送能力决定 |
| inactive / 不存在 | 任意 | blocked | “当前无法添加” | 不提供新的私聊入口 |
| inactive / 不存在 | outgoing | none | “申请已发送” | 不重复申请 |
| inactive / 不存在 | incoming | none | “对方向你发来了申请” + 前往好友页面 | 不重复申请 |
| inactive / 不存在 | none | none | “添加好友” | 无现有好友私聊入口 |

Active 好友优先于隐藏和联系限制。联系限制只在双方不是 active 好友时替代“添加好友”。

当前成员本人继续显示“我”，不显示任何好友操作。

## 课程成员关系摘要契约

新增一个只供 authenticated 成员调用的批量读取 RPC。建议名称：

```text
list_course_member_relationships(target_course_id uuid)
```

RPC 为课程中除调用者之外的成员返回：

| 字段 | 类型 | 说明 |
|---|---|---|
| `member_id` | `uuid` | 课程成员 ID |
| `relationship_status` | `text` | `none`、`outgoing_request`、`incoming_request` 或 `friend` |
| `restriction_status` | `text` | `none` 或 `blocked` |
| `send_status` | `text null` | `allowed`、`blocked`、`readonly`；没有可打开私聊时为 null |
| `conversation_id` | `uuid null` | 已有私聊 ID；不存在时为 null |

### 权限要求

RPC 必须在数据库内验证：

- 调用者已登录并完成 onboarding；
- `target_course_id` 对应课程存在；
- 调用者当前确实是该课程成员；
- 课程属于调用者的当前学校；
- 返回范围只包含该课程成员；
- 不返回邮箱、好友备注、隐藏偏好、学校绑定或其他无关资料。

函数必须固定安全的 `search_path`，撤销 public 与 anon 执行权限，只授予 authenticated。客户端传入的成员 ID 或页面上是否显示按钮都不能替代数据库权限判断。

### 数据一致性要求

- 一次 RPC 调用必须在同一个数据库快照中计算关系状态，避免分别查询好友、申请和拉黑列表后产生矛盾结果。
- Active 好友必须返回 `relationship_status = 'friend'`，即使存在联系限制。
- Active 好友必须能够返回已有 `conversation_id`。若历史数据违反该不变量，页面不得拼接无效链接。
- 待处理申请按无序成员对判断，任一方向都不能再次显示“添加好友”。
- 好友申请写入 RPC 继续检查 active 好友和 active 申请，页面状态不能成为唯一保护。

## 邮箱搜索行为

- 搜索到 active 好友时显示“你们已经是好友”，不显示申请表单。
- Active 好友存在隐藏或联系限制时，仍保持好友身份；可以另外显示限制说明。
- 搜索到 outgoing 或 incoming 申请时，不显示新的申请表单。
- 搜索到受限制的非好友时显示当前无法添加。
- 邮箱搜索结果继续只返回允许公开的成员资料，不把邮箱回显到页面、URL 或浏览器存储。

## 私聊入口与发送失败

### 已知发送限制

课程成员列表中的“发消息”进入 `/messages/{conversationId}`。如果服务端读取到 `send_status = 'blocked'` 或 `readonly`：

- 历史消息继续可见；
- 页面说明当前限制；
- 输入框和发送按钮禁用；
- 不创建一条已知必然失败的本地消息。

### 提交后失败

只有在用户提交时页面认为允许发送、但发送请求实际失败时，才保留失败的本地消息：

- 消息前显示红色感叹号；
- 同时提供“发送失败”的可见文本或无障碍名称，不能只依赖颜色；
- 网络错误或临时服务错误允许手动重试；
- 重试复用原 `clientMessageId`，保证幂等并避免重复消息；
- `not_allowed` 表示关系或权限已经变化，显示明确原因，不提供无意义的重复重试；
- 服务端成功消息到达后，按 `clientMessageId` 移除对应本地失败或发送中状态。

## 失败与降级

- 课程主体数据读取失败时沿用现有课程页面错误边界。
- 课程关系摘要读取失败时，课程内容仍可查看；其他成员显示“关系状态暂不可用”，不显示“添加好友”或“发消息”。
- 好友关系存在但 `conversation_id` 缺失时显示“关系数据异常”，不生成聊天链接。
- 页面加载后关系发生变化时，写入 RPC 的实时检查优先；旧页面不得绕过好友申请或消息发送规则。
- 客户端不展示数据库、Supabase 或权限函数的原始错误。

## 验收与测试优先级

### P0：发布阻断

- 课程群中的普通 active 好友显示“已是好友”和正确的私聊链接，不显示“添加好友”。
- 隐藏的 active 好友仍被识别为好友。
- 我拉黑好友、好友拉黑我及双方互相拉黑时，仍显示“已是好友”和私聊入口。
- 上述受限好友能查看历史，但不能输入或发送新消息。
- 邮箱搜索中的普通、隐藏或受限 active 好友均不显示申请表单。
- 普通非好友才显示“添加好友”。
- incoming 或 outgoing 待处理申请均不显示“添加好友”。
- 非课程成员、跨校成员和伪造课程 ID 不能读取课程关系摘要。
- RPC 不泄露邮箱、备注、隐藏偏好或其他课程成员范围外的数据。
- 直接调用好友申请或消息发送 RPC 仍不能绕过 active 好友、申请、拉黑和学校权限。

### P1：重要失败与并发

- 页面加载后申请被接受，旧页面提交重复申请时数据库返回已有好友，不创建新申请。
- 页面加载后好友被删除或学校上下文变化，旧聊天页发送时数据库拒绝写入。
- 课程关系摘要失败时显示“关系状态暂不可用”，不错误展示“添加好友”。
- Active 好友缺少私聊 ID 时不生成无效链接。
- 临时发送失败显示红色失败标记，并可复用同一个 `clientMessageId` 重试。
- `not_allowed` 失败说明关系状态变化且不可重试。
- 重试和随后到达的服务端消息不会生成重复记录或重复气泡。

### P2：体验与可访问性

- 红色感叹号具有可见说明或无障碍名称，键盘用户可以访问允许的重试操作。
- 状态文字与按钮在窄屏课程成员列表中仍可读、可操作。
- 课程成员关系使用一次批量 RPC，不为每位成员分别查询。
