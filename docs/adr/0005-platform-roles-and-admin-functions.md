# 平台角色存在数据库里，管理操作只经固定函数

团队成员需要做日常运营——录课、切换学期、管理开放学校——但不应该为此拿到 Supabase 后台权限。为此引入三级平台身份（普通成员 / 管理员 / 所有者），存在 `public.platform_roles` 表里；网站的 `/admin` 页只通过一组固定的 `SECURITY DEFINER` 函数改数据，每个函数开头校验调用者身份，每次操作写入 `admin_audit_log`。

## 为什么身份放在单独的表里

- **不能放 `profiles`**：成员自己能改自己的资料，等于谁都能自封管理员。
- **不能放 Auth 的 `user_metadata`**：成员同样能用 `auth.updateUser()` 改它。
- **不放 `app_metadata` / JWT 自定义声明**：那样能省一次查询，但撤销身份要等令牌过期才生效；而且只能用 service_role 写，网站上的「任命管理员」就又回到了需要后台权限的老路。
- 表对客户端完全关闭（不授权、不建策略），读写都经函数，身份变更立即生效。

## 为什么是固定函数，而不是给管理员开放写表的 RLS 策略

- 管理员碰不到原始表，只能做预设好的几件事，也读不到其他成员的邮箱。
- 规则集中在函数里：录课函数逐行校验长度，切换学期函数校验格式并在同一次调用里物化新学期课程。这些规则不会因为某个页面漏写而失效。
- Server Action 是任何人都能直接 POST 的公开入口。授权落在数据库，就不依赖页面有没有渲染表单。

## 为什么学校与域名只给所有者

开放学校和邮箱域名直接决定谁能登录——登录页与 Auth Hook 读的是同一份白名单。误删最后一个域名等于把整所学校锁在门外。这类操作少、影响大，留给所有者；函数本身也拦住了「删掉开放学校的最后一个域名」。

## 代价

- 管理员账号和普通账号一样只靠学校邮箱验证码登录，邮箱被盗对方就能进管理页。缓解：能做的事有限，每一步有记录，所有者随时可以撤销。相比让协作者持有 Supabase 后台权限——能看到 service_role key、关闭 RLS、读取全部邮箱——风险面小得多。
- 只能有一位所有者，且网站上撤不掉所有者，避免把自己锁在门外。转让所有权在 SQL Editor 里做。
- 第一位所有者只能在 SQL Editor 里手工指定一次。
- 暂不按学校划分管理范围。等到请各校同学帮忙运营时，给 `platform_roles` 加一列 `school_id`，并在各函数里比对即可。
