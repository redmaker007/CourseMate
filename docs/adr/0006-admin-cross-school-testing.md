# 管理员跨校测试：业务学校由数据库里的当前学校决定

团队成员的学校邮箱都属于某一所学校，却需要用自己的账号体验另一所学校的课程、好友和私聊。为此允许管理员与所有者选择一所开放中的「测试学校」：登录、成员账号绑定与 Auth Hook 仍按真实邮箱归属；课程与社交功能一律读取数据库给出的**当前学校**——普通成员就是邮箱归属，管理员在测试时是所选学校。

## 为什么判断落在数据库，而不是页面

课程群与私聊共用 `messages` 表，读写都经 RLS 与 `send_conversation_message`。只改页面上显示的学校，挡不住仍开着的旧页面、直接 REST 调用和 Realtime 推送。所以 `current_school_id()` 本身改为返回当前学校，课程访问、同课同学可见、按邮箱找人、好友申请、私聊发送都据此重新计算，每次请求实时生效。

## 规则

- **谁能切**：只有 admin / owner，只能切到开放中的学校；选回邮箱归属学校即退出测试。每次切换写入操作记录。
- **影响范围**：对这个账号的所有会话、所有设备同时生效。
- **自动失效**：撤销管理员身份时测试状态随角色一起删除；测试学校被关闭时清除，重新开放也不会悄悄恢复。
- **数据保留，权限重算**：选课、好友关系和消息都保留。课程群只在当前学校与课程所属学校一致时可读可写；私聊历史始终对参与者可读，新消息要求**双方当前学校相同**；新的好友申请同样要求同校。
- **自我保护不受学校限制**：对已有往来（申请、私聊、已拉黑）的成员，切校后仍能拉黑、解除拉黑、拒绝待处理的申请。
- **管理员身份不附带任何读取权**：测试时看到的只是「以该校成员身份」本来就能看到的内容，不能读取别人的私聊。

## 否决的做法

- **直接改 `member_accounts.school_id`**：那一列是登录绑定，Auth Hook 与会话校验都依赖它与邮箱域名一致；改掉等于伪造身份，而且切回时容易留下不一致。
- **为每所学校另建测试账号**：需要真实的学校邮箱，团队拿不到。

## 代价

- **测试写入的是真实数据。** 本地、预览与生产目前连接同一个 Supabase 项目，测试时发的课程消息、好友申请会出现在该校真实学生面前。能用测试课程时尽量用测试课程。
- 与真实学生建立的好友关系在切回本校后，**对方那边的私聊也会变成只读**，直到管理员再次进入该校。
- 页面需要多一次 RPC 读取当前学校；读取失败时按未登录处理，与读取 onboarding 状态失败一致。
