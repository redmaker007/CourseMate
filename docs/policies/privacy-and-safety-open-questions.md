# App Store 上架前的内容治理与隐私：待决定事项

日期：2026-11-22。这份文档列出原生 iOS App 上架前**要由项目负责人决定**的事情。拿到答案后把结论写进 runbook／政策文档，再实现。当前进度见 [STATUS](../STATUS.md)。

## 依据：Apple 审核指南 1.2（2026-11-22 核对原文）

做用户生成内容的 App 必须有四样东西：

1. 过滤不当内容、阻止其发出的方法；
2. 举报不当内容的机制，并**及时**回应；
3. 拉黑辱骂用户的能力；
4. 公开的联系方式。

1.2 原文**没有**固定的 24 小时时限，也没有要求用户协议（EULA）。但它写明违反服务条款或社区规范的内容由开发者负责删除；1.5 要求 App 内和 Support URL 都能方便地联系到开发者；5.1.1(v) 要求可以在 App 内删除账号。

| 要求 | 现状 |
|---|---|
| 过滤 | **缺**。只检查长度和空白，防 HTML 注入。见下文第一部分 |
| 举报 | 已支持私聊消息、好友申请、资料。课程群消息在 PR #67 补齐，迁移还没应用到生产 |
| 及时回应 | **缺**。有举报记录，但没有指定处理人，没有处理工具，也没有响应时限。见第二部分 |
| 拉黑 | 已有。单向拉黑后双方不能再私聊，但课程群里仍能看到对方发的消息 |
| 联系方式 | **缺**。见第二部分 |
| App 内注销 | 已有接口（PR #58）；App 页面由丹尼实现 |

## 第一部分：内容过滤方案（等你确认后再实现）

### 先要知道的一个事实

学生端拿着自己的 JWT，可以绕过网页和 App，**直接调用** Supabase RPC，比如 `send_conversation_message`、`send_friend_request`，或者直接更新 `profiles`。所以，过滤如果只写在网页 Server Action 或移动 API 里，就能被绕过。要做到“阻止发出”，检查必须放在数据库函数或表约束里。只在客户端提示的过滤，不算真正拦截。

### 选择一：发送时拦截，还是发出后标记

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A. 发送时拦截**（推荐起步） | 命中词表就拒绝发送，返回新状态 `content_rejected`，界面提示“内容包含不允许的词语，请修改后再发” | 不当内容不会出现在任何人屏幕上，完全符合“阻止发出”；只改服务端，加一个错误码 | 会误伤正常内容；改个写法就能绕过；用户被拒时容易沮丧 |
| B. 发出后标记／折叠 | 照常保存，命中的消息对接收者折叠成“可能含不当内容，点此查看”，同时进审核队列 | 不误拦，接收者自己决定看不看 | 内容其实已经发出，是否满足“阻止发出”有争议；网页和 App 都要做折叠界面，丹尼工作量更大 |
| C. 两级 | 严重词（仇恨蔑称、威胁、性剥削等）直接拦截，较轻的词折叠 | 兼顾两边 | 两套逻辑，维护最复杂 |
| D. 第三方 AI 审核（如各家 moderation API） | 每条消息发给外部服务打分 | 能识别变体和语义 | 新增重要依赖；消息正文要发给第三方，隐私政策和 App 隐私标签都要改；增加延迟和费用 |

**推荐 A**：先上一份小而准的严重词表，再加上已有的举报和拉黑兜底。审核时这样足以说明“有过滤机制”，误伤面也最小。之后如果误伤或漏网明显，再考虑 C。

### 选择二：词表放在哪里

| 位置 | 优点 | 缺点 |
|---|---|---|
| **数据库表 `content_filter_terms`**（推荐） | 发送 RPC 在同一事务里检查，网页、App、直接调 RPC 全部覆盖；改词表不用重新部署；普通成员读不到（RLS 全关），只有 service_role 和数据库负责人能改 | 要写迁移、PGlite 测试；词多了要注意匹配性能（小词表没问题） |
| 仓库里的 TS 常量 | 改动简单，代码审查能看到每个词 | 挡不住直接调 RPC，**做不到真正拦截**；改词要重新部署；词表随源码公开 |
| 外部服务 | 不用自己维护 | 同方案 D 的缺点 |

### 选择三：覆盖哪些内容

推荐：课程群和私聊消息（`send_conversation_message`）、好友申请附言（`send_friend_request`）、显示名和专业（`profiles` 写入）。好友备注只有本人可见，可以不管。

### 误伤怎么处理（建议）

- 匹配前先规范化：转小写，全角转半角，去掉空格、标点和零宽字符。这样可以防止用插空格之类的写法绕过。
- 英文按整词匹配，避免 Scunthorpe 问题（正常单词里恰好含有敏感词的字母序列）；中文按子串匹配，所以中文词要选得很准。
- 被拒时只提示“包含不允许的词语”，不回显是哪个词，以免被拿来试探词表。
- 不记录被拦截的原文，只计数，避免为过滤额外保存用户内容。
- 用户觉得被误伤，可以发邮件到公开联系邮箱；由负责人调整词表。
- 词表变更要留记录：谁在什么时候改了什么。最简单的做法是只通过迁移或受控 SQL 修改。

### 需要你回答

1. 选 A／B／C／D 哪一个？
2. 词表放数据库（推荐）还是仓库？
3. 覆盖范围是否同意推荐的三类？
4. 词表由谁整理（中文和英文都要），谁有权修改？
5. App 端要处理新错误码 `content_rejected`，需要通知丹尼，由谁对接？

## 第二部分：举报处理与公开联系渠道

现在举报只会写进三张表，负责人能用 SQL 按 reportId 查到（见[移动举报交接](../handoffs/mobile-reporting-api.md)“后台定位”一节）。但没有人负责，没有提醒，也没有处理工具。

### 需要你回答

1. **谁处理举报？** 主处理人是谁，有没有备份人。按 [CONTRIBUTING](../../CONTRIBUTING.md)，证据只应该给有数据库权限的人看。
2. **多久回应？** Apple 只写了“及时”。建议对外承诺“通常 24–48 小时内查看”，具体由你定，承诺了就要做得到。
3. **怎么知道有新举报？** 选项：(a) 处理人每天查一次 SQL（不用写代码）；(b) 新举报时发邮件提醒（要新增发信逻辑和密钥）；(c) 做管理后台举报列表（工作量最大）。建议先 (a)，写进 runbook。
4. **能采取什么处置？** 现在能做的：数据库负责人把举报状态改成 `dismissed` 或 `actioned`，用 SQL 软删除消息（`deleted_at`）。现在**做不到**：封禁或踢出用户（没有封号功能）、通知举报人处理结果。上架前要不要补“封禁账号”？1.2 写明违规内容由开发者负责删除；拉黑只是用户自己的手段。
5. **对外联系邮箱用哪个地址？** 要求真实、有人看。最好用团队地址，而不是某个人的私人邮箱。这个地址会出现在隐私政策页、App 内和 App Store 的 Support URL。
6. **Support URL 用什么？** 可以直接用 `/privacy#contact`，也可以另做一个 `/support` 页。
7. **举报证据保留多久？** 现在没有期限：处理完不释放，注销后也只是匿名保留。要不要定一个期限，比如处理完一年后删除正文？定了才能写进隐私政策。

拿到答案后要做的事：

- 把邮箱填进 `src/features/legal/public-contact.ts` 的 `PUBLIC_CONTACT_EMAIL`。网页隐私政策页会自动显示；登录页和“我的”页底部已有“隐私政策”链接。App 内由丹尼加链接或联系入口。
- 新写 `docs/runbooks/report-handling.md`：谁处理、多久看一次、查询 SQL、怎么改状态、怎么删消息、怎么回复用户。

## 第三部分：隐私政策里拿不准、需要你确认的事实

隐私政策页 `/privacy` 按代码和迁移写成（来源见[隐私政策事实来源](privacy-policy-sources.md)）。下面这些事实从仓库里查不到，需要你确认：

1. **“我们”是谁？** App Store 卖家是个人还是团队或公司？政策里要不要写主体名称？
2. **联系邮箱**：同第二部分第 5 题。
3. **服务商的保留期**：Supabase 是哪个付费档（决定备份保留几天）、Vercel 日志保留多久、Brevo 发信日志保留多久。政策里现在只笼统写了“按其自身策略保留一段时间后删除”。
4. **App 里注销入口的位置**：例如“我的 → 设置 → 注销账号”，需要丹尼确认。政策里现在只写了“在 iOS App 内”。
5. **网页端要不要也提供注销？** Apple 只要求 App 内能注销。现在网页用户没有自助注销，只能等联系邮箱公布后发邮件申请。
6. **年龄**：政策写了“不面向 13 岁以下”。App Store 年龄分级打算选多少？有聊天功能，通常不会低于 12+／17+。
7. **要不要英文版？** 用户在美国大学，审核员也可能看英文。现在只有中文。
8. **头像**：`profiles.avatar_url` 字段存在，但没有上传或编辑入口，所以政策里没写头像。如果以后开放头像，要补上。
9. **App 端会不会接入崩溃统计或分析 SDK**（比如 Sentry、Expo 自带服务）？会的话，政策和隐私标签都要加“诊断数据”。需要丹尼确认。
10. **私聊 720 小时清理**：已有能力，但没有定时任务，所以政策写的是“保留到注销”。如果以后启用，要更新政策。
11. **适用地区和法律**：要不要提 CCPA 等？是否需要有人做法律审阅？这份政策没有经过法律审阅。
