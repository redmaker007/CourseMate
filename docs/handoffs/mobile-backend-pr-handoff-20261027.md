## 本轮修复对前端的影响

- 首次有效验码后成员绑定缺失／不匹配：403 `membership_denied`，展示成员不可用；读取异常／畸形 RPC：503 `temporarily_unavailable`，提示稍后重新发码，不重试已经消费的验证码。失败均不返回 token，不把临时错误当成确认失效。
- 刷新成功先保存整对新凭据，再检查成员；暂时网络错误不锁旧缓存，明确会话／准入失效才按契约锁定。
- 屏蔽只改变显示和通知资格，拉黑禁止双方新消息，个人清空只影响本人历史；不得在客户端混用。
- 主动退出保留但锁定本人离线库，重新联网登录同账号验证后解锁；永久注销 completed 后删除本人凭据／缓存并清通知。未知注销结果先查保存的随机回执，不能猜成功或回滚。
- 通知只展示发送者＋“发来一条消息”，不携正文。冷启动／后台／重复点击先核验当前账号，再通过消息接口复核目标权限；收到通知不直接插入消息或累加未读。

指定测试项目是 CourseMate-test，项目标识 `cqrlxcxcgrcoamqnjkwu`；测试前核对实际运行的项目地址。Shell 或部署环境已有变量可能优先于 `.env.local`，必须检查最终解析目标，避免测试脚本误用另一环境。

本地从隔离工作树运行，配置文件是该目录的 `.env.local`，字段参考 `.env.example`。仅按变量名交接，真实值不进 Git、PR、Notion、截图或日志：

- 服务端管理 key 存在 SUPABASE_SERVICE_ROLE_KEY 变量中；可使用项目对应的新版 secret key，仅后端持有。

## 迁移、合并与部署顺序

1. Code Owner 先审核本 PR 的认证／权限／schema 改动；本轮 agent review 不替代仓库要求的 owner 审批。
2. 在匹配的测试库核对完整历史及托管 Auth／Storage 结构，再按顺序应用完整迁移。本 PR 新增 `202610260001_permanent_account_deletion.sql`、`202610260002_mobile_push.sql`；严格审查优化已包含在尚未进入 main 的后者中。不要重写已部署迁移记录。
3. 用 Supabase CLI 从目标测试库重新生成 database.ts，检查差异和权限后提交。当前新增 RPC 用窄端口调用，生成文件未手改；此项仍待真实环境完成。
4. 配置服务端变量并发布测试后端，验证 JSON 401／403／405／503、网页回归、会话与真实业务；尚未迁移或配置的新功能不可假报可用。
5. 接通受保护的 POST `/api/mobile/v1/internal/push-dispatch` 定时恢复调用，监控失败／未知回执和积压；只有 after 不能保证进程中断后恢复。秘密放请求头，不带 body／URL 参数，不交前端。
6. 与原生客户端完成登录→课程／好友→消息／举报→退出／换号→离线恢复→注销→推送的联合验收，再判断生产发布条件。合并／生产迁移／发布另行处理。

## 回滚与最重要的失败情况

应用可以回退，但已执行的永久账号／正文删除不能靠回退代码恢复。优先保持功能关闭／隔离测试环境，不能用生产账号试删。数据库依赖先核对，再发布应用；回滚前停恢复调度，不盲目删除 schema／队列或重写迁移历史。

排障按数据流定位：请求身份／准入 → 业务 RPC／RLS → 消息或注销事务 → 回执／同步 → 推送队列 → APNs → 客户端账号／缓存／导航。推送失败不重写原消息；网络未知结果按回执／租约恢复，APNs 接受不代表用户已经看到通知。
